AI Implementation Assistant

Shipped · in active use

My role: owned the architecture, retrieval design, and security & privacy layers; directed engineering end to end.

Problem

Implementation, support, and sales teams lost significant time searching across 200+ documents, recorded calls, and product videos to answer recurring questions — with inconsistent answers.

What I built

A production Retrieval-Augmented Generation (RAG) assistant. Content is chunked, embedded, and stored in a vector database; a query runs hybrid (semantic + keyword) retrieval, and an answering model responds grounded only in retrieved context. Access is invite-only, with rate limiting, input sanitisation, and a server-side privacy layer that strips any customer-identifying detail before a response leaves the server. It also answers questions about uploaded screenshots (vision).

Impact

In active use across 7 functional teams (30+ members), with 1,000+ questions answered — 94% grounded in retrieved context, not free-form generation — replacing scattered manual lookups across 200+ sources with consistent, cited answers.

Key decisions & trade-offs

Privacy enforced in the pipeline, not just the prompt.

Prompt instructions alone leaked occasionally — dominant source context can override an instruction. So identifier-stripping is enforced server-side on the response, making it deterministic rather than probabilistic.

Didn't just widen retrieval to fix answer quality.

Raising top-k adds noise and models get "lost in the middle." I prioritised retrieval quality (hybrid search, thresholding, a QA eval set to measure every change) over brute-force recall.

Sequenced the hard rebuild for launch, not now.

A full data-layer re-processing would improve quality but is a pre-launch investment with real cost and risk. I shipped the lower-risk path first and scheduled the deeper fix against an eval set — avoiding premature optimisation.

Designed for resilience and cost: provider fallback + a confidence gate.

The answering layer fails over across multiple LLM providers, so a single provider outage never takes the assistant down. A retrieval-confidence threshold routes low-confidence questions to a general-knowledge path instead of forcing a weak, hallucination-prone answer — a correct "not sure" beats a confident wrong one.

Automated Competitive-Intelligence System

Shipped · rolling out

My role: owned the thesis, architecture, classification design, and rollout across functional teams.

Problem

Competitive tracking was manual, inconsistent, and always out of date — leaving product, sales, and GTM decisions under-informed.

What I built

A scheduled pipeline that collects from 25+ competitor sources daily, detects genuine changes via hash comparison (ignoring noise), classifies each change against a 214-capability taxonomy using a grounded contract that requires verbatim source quotes, then severity-routes findings (P0–P3) into the right output — priority alerts, a weekly digest, and a monthly rollup.

Impact

Fully automated on a schedule: 158 runs over ~6 weeks surfaced 90 signals — including 5 urgent (P0) alerts — from 50+ tracked sources (31 competitors across 3 tiers), replacing ~16 hrs/week of manual, inconsistent tracking. Now used across product, engineering, leadership, sales, and partner teams.

Key decisions & trade-offs

Change-detection before classification.

Classifying everything daily would be noisy and wasteful. In practice hash-diff filters ~90% of observations (≈3,965 unchanged vs. ≈428 new/changed) before the model runs — so only genuine changes reach classification, keeping cost low and signal high.

A grounding contract to stop hallucinated intel.

Competitive claims have to be trustworthy, so every classification must cite a verbatim source quote. If it can't quote it, it doesn't report it.

Severity routing so it drives action, not noise.

Not every change deserves an alert. P0–P3 routing sends urgent moves to a priority channel and rolls the rest into digests — respecting the reader's attention.

GTM Launch: Scheduler v2 & Trigger Merge

Shipped · zero critical issues

My role: owned positioning & messaging, the release plan, alpha/beta programmes, and sales & support enablement.

Problem

Two major capabilities — a rebuilt Scheduler and event-based Trigger Merge — were ready for 1,500+ customers. Shipping them without clear positioning, phased validation, and enablement risked confused users, avoidable support load, and post-release fires.

What I did

Ran both launches end to end: sharpened the positioning and messaging, wrote the release notes, staged an alpha then a beta cohort to validate on a small blast radius before general availability, and enabled sales and support so every team could sell and troubleshoot from day one.

Impact

Both features shipped to 1,500+ customers with zero critical post-release issues, and support was equipped to answer customer questions on day one instead of escalating.

Key decisions & trade-offs

Phased rollout over a big-bang launch.

Alpha then beta cohorts surfaced real-world issues on a small blast radius before GA — which is why both features shipped with zero critical post-release issues rather than firefighting after launch.

Enablement is part of the launch, not an afterthought.

Sales and support were trained and equipped before GA, so customer questions were handled on day one instead of turning into escalations and churn risk.
